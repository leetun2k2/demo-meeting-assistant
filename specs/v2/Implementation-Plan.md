# Implementation Plan — Task Breakdown and Task-Level Design (v2: Meeting Intelligence)

Date: 2026-11-05
Status: Draft plan; no tasks implemented or verified.
Sources: [PRD v2.1](PRD.md), [Requirement Findings](Requirement-Findings.md), [Technical Design](Technical-Design.md).

## Basis and constraints

This plan implements the accepted v2 Technical Design in place on top of the already-implemented, already-verified v1 pipeline (see [specs/v1/Implementation-Plan.md](../v1/Implementation-Plan.md) and the README's "pipeline has since been exercised against a live Gemini account" note). It does not reopen any v1 decision: Record/Upload input, key storage, the 20 MiB/5-minute limits, the three result statuses, and the single-request `POST /api/process-meeting` flow are all unchanged.

Everything below only extends: the Gemini 3.5 Flash-Lite structured-output schema/prompt (same call, more fields), the shared result types, and the presentation layer (a new Output Page replacing `ResultsPanel.tsx`). No new route, model, library, or persistence mechanism — see Technical Design's "Recommended direction" and "Trade-offs" for why. The user authorized full-flow implementation with "pick the simplest/easiest way, scope is a demo"; where this plan calls for a local judgment call, it resolves toward the smaller, more conventional option rather than the more complete one.

Inspected repository facts grounding this plan: current `MeetingSummary`/`ActionItem`/`TranscriptSegment` in [lib/types.ts](../../lib/types.ts); the one `RESPONSE_SCHEMA`/`SYSTEM_INSTRUCTION`/`validateSummary()` in [lib/meeting/gemini.ts](../../lib/meeting/gemini.ts); `normalizeTranscript()`'s discarded `endMs` in [lib/meeting/geminiTranscribe.ts](../../lib/meeting/geminiTranscribe.ts); the pass-through route in [app/api/process-meeting/route.ts](../../app/api/process-meeting/route.ts); today's `ResultsPanel.tsx`; and `MeetingWorkspace.tsx`'s existing `audio`/`previewUrl`/`result`-persistence state. No provider SDK, chart library, or state-management dependency is installed ([package.json](../../package.json)).

## Integration agreement

Settle these shared shapes up front so Task 1 and Task 2 can proceed from the same contract (full field-level detail is in Technical Design's "Data contract changes" and "Validation policy" — this is the short reference version, not a restatement):

- `TranscriptSegment` gains optional `endMs`. `ActionItem` gains `status: "open" | "done"`, always client-initialized to `"open"` — never requested from or trusted from Gemini.
- `MeetingSummary` gains `title`, `executiveSummary`, `speakerNames: {speakerLabel, resolvedName}[]`, `risks`, `unresolvedQuestions`, `nextSteps`, `keyMoments`, `followUpEmail`; `decisions` changes shape from `string[]` to `{text, atMs?}[]`. `discussions`/`nextSteps` stay `string[]`.
- One pure `displaySpeaker(label, speakerNames)` function is the only place that turns a raw `"Speaker N"` key (or `"Unknown"`, or an already-resolved free-text name) into what the UI shows. Both tasks must route every speaker-label render through it — this is what makes transcript/action-item name consistency (AC-05) hold structurally.
- `MeetingResult`'s outer shape (`status`, `transcript`, `summary`, `summaryError?`, `warnings?`) and the three status values are unchanged from v1.

## Task 1 — Extend the Meeting Intelligence contract and the Gemini analysis call

**Outcome:** `summarizeTranscript()` returns the full v2 `MeetingSummary` (title, executive summary, speaker resolution, decisions/risks/questions with optional transcript references, key moments, next steps, follow-up email) from the same single Flash-Lite call, with the same all-or-nothing-for-required-fields / lenient-for-optional-fields failure semantics already established in v1. Independent of Task 2 — it only changes the shape and content of data the UI will consume, not how the UI is built.

**Approach and constraints:**

- In `lib/types.ts`, apply the Integration Agreement shapes above. Keep `MeetingResult`/`MeetingStatus` untouched. Add the small supporting types (`SpeakerNameResolution`, `ReferencedInsight`, `KeyMoment`, `FollowUpEmail`, `ActionItemStatus`) next to the types they extend, following the file's existing flat-interfaces style — no namespacing or barrel file needed for six small types.
- In `lib/meeting/geminiTranscribe.ts`, stop discarding `endMs` in `normalizeTranscript()`'s final `.map()` — this is a one-line change (the value is already computed in `WorkingSegment`). Do not otherwise touch the STT request/response handling; this task does not change the Transcribe call, diarization, or timing logic.
- In `lib/meeting/gemini.ts`:
  - Extend `RESPONSE_SCHEMA` per Technical Design's schema section. `actionItems` schema stays exactly as today (no `status` property — it is never part of the model's output). `decisions` becomes `array<object{text, atMs?}>` instead of `array<string>`. Add `title`, `executiveSummary`, `speakerNames` (array of `{speakerLabel, resolvedName}`, `resolvedName` nullable), `risks`, `unresolvedQuestions` (array of `{text, atMs?}`), `keyMoments` (array of `{atMs, title, description}`, all required), `nextSteps` (`array<string>`), `followUpEmail` (`{subject, body}`). Keep `required` arrays accurate per field (see validation policy below — what's structurally required in the schema should match what `validateSummary()` treats as hard-failing).
  - Before building the request, compute the transcript's distinct `speaker` values in first-occurrence order (the same labels `normalizeTranscript()` already assigned) and interpolate that exact list into `SYSTEM_INSTRUCTION`, instructing the model to return exactly one `speakerNames` entry per listed label. Extend the instruction with the FR-02 resolution rules — reuse the PRD's own rule/scenario wording (it is already precise and example-driven) rather than writing new prose from scratch: resolve a name only on direct self-introduction or a clearly-answering context, never from a name merely mentioned about someone else, keep one resolved identity per label for the whole transcript, and default to unresolved when uncertain.
  - Add instructions distinguishing: decisions (actually agreed, not proposed) — unchanged from today, now paired with an optional supporting timestamp; risks/blockers and unresolved questions as only those with direct transcript grounding; key moments as genuinely notable points (the PRD's own examples — budget discussion, final decision, task assignment) each with a real timestamp; next steps as the model's own recommendations, explicitly distinguished from the Action Items list so the model does not duplicate entries across the two; the follow-up email as short, professional, in the meeting's dominant language, grounded only in the already-extracted fields (not an independent re-read of the full transcript). All of these inherit the existing "never invent content the transcript doesn't support" instruction already present — do not restate it per field.
  - Extend `validateSummary()` exactly per Technical Design's "Validation policy" subsection: `title`/`executiveSummary`/`followUpEmail.subject`/`followUpEmail.body` are required nonempty strings (missing/blank → `GeminiError`, same `summary_failed` outcome as today's required-field failures). `speakerNames` entries are validated for shape; an entry for a label not in this transcript is ignored, and any transcript label missing from the model's array defaults to `resolvedName: null` (never fail the summary over a missing speaker-name entry). `decisions[].text` / `unresolvedQuestions[].text` / `risks[].text` are required nonempty strings per item (malformed item text is a hard failure, consistent with today's array-item validation); each item's `atMs`, when present, must be a finite number `>= 0` or is dropped (set to `undefined`) without failing the item. `keyMoments[]` entries with a missing/invalid `atMs` are filtered out of the array rather than failing the whole summary. After validation, set every `actionItems[i].status` to `"open"` in code — this is not read from the parsed JSON at all.
- In `app/api/process-meeting/route.ts`, no behavior change is expected — verify it compiles against the extended types and still returns `summarizeTranscript()`'s result verbatim. If TypeScript surfaces a mismatch, the fix belongs in the type/validator, not in route-level reshaping.

**Risks:** The schema now has roughly three times as many fields as v1's; there is no executed evidence here that Flash-Lite reliably fills every optional field or keeps the speaker list honest for a given account — this is the same category of provider-behavior risk the v1 plan already flagged for a smaller schema (see v1 Implementation-Plan Task 2 "Completion" note and the README's "Known limitations"). Report actual behavior after a real run rather than assuming schema compliance.

**Completion:** `summarizeTranscript()` compiles and type-checks against the new `MeetingSummary`, returns every new field in the happy path, and still produces `summary_failed` (preserving the transcript) for a malformed required field, exactly mirroring today's failure contract. A missing/invalid optional field (one bad `atMs`, one bad `keyMoments` entry, one unresolved speaker) degrades that one value, not the whole result. This is implementation completeness against the schema contract, not evidence of real-provider output quality — that is for execution/testing.

## Task 2 — Rebuild the Output Page and wire it into the workspace

**Dependencies:** Consumes the types/fields Task 1 adds; can be built/reviewed against those types once they exist, in parallel with Task 1's prompt/validation tuning if useful, but cannot be meaningfully exercised end-to-end until Task 1 is in place.

**Outcome:** `components/ResultsPanel.tsx` is replaced by an Output Page presenting Meeting Overview, Meeting Intelligence, Additional Insights, and Quick Actions per PRD §2.2/§4 and Technical Design's "Output Page structure", with the interactive behaviors FR-05/FR-06/FR-11 require (editable/completable action items, transcript search/filter, jump-to-audio/jump-to-transcript, copy/download/follow-up actions) — all client-side, no new backend surface.

**Approach and constraints:**

- Rename/replace `ResultsPanel.tsx` with the new Output Page component (same mount point in `MeetingWorkspace.tsx`'s Section 4). Keep the existing per-status branches (`no_speech` / `summary_failed` / `completed`) and their current messages; the new content only applies within the `completed` branch where `result.summary` is non-null.
- Single-scroll layout, section order = PRD visual hierarchy (Level 1 → 2 → 3) — no tab/view-switching state. Reuse the existing `<details>`/`<summary>` pattern for the lowest-priority disclosure content (Raw JSON, and the Follow-up Email reveal — see below), matching today's component's own convention instead of introducing a modal or accordion library.
  - **Meeting Overview:** title and executive summary first (FR-01 — "must be the most prominent information"), then four stat values: duration, speaker count, decision count, action-item count. Counts are `array.length` over `result.summary`. Duration: compute from the transcript's last segment (`lastSegment.endMs ?? lastSegment.startMs`); if `transcript.length === 0`, omit the duration stat entirely rather than showing `0:00` (reuse `formatClock` from `lib/format.ts`). Do **not** read `<audio>` element `duration` for this — Technical Design records why (unreliable/`Infinity` for freshly recorded `MediaRecorder` WebM blobs until seeked).
  - **Meeting Intelligence:** Key Discussion Points (unchanged list rendering), Decisions Made (render `.text`, add a "View in transcript" control when `.atMs` is present), Action Items (extend today's table: an inline-editable task/assignee/deadline cell set, per the PRD "user can edit" requirement — simple controlled `<input>`s swapped in on a per-row edit toggle is enough, no form library — and a checkbox bound to `status`, toggling between `"open"`/`"done"` with a struck-through/dimmed style for done rows; keep the existing "Copy Action Items" affordance as one of the Quick Actions rather than duplicating it here), Transcript (add a text `<input>` filtering segments by case-insensitive substring match on `text`, and a speaker `<select>` populated from the distinct resolved display names present, both purely client-side array filters over the existing `result.transcript`; render every speaker label and action-item assignee through the shared `displaySpeaker()` function).
  - **Additional Insights:** Risks & Blockers, Unresolved Questions (same "View in transcript" control where `.atMs` is present), Key Moments (ordered list — timestamp, title, description — each row clickable to jump; explicitly not a timeline/chart widget per Requirement Findings finding 1), Suggested Next Steps. Every list here renders the existing project convention for an empty collection (a muted one-line message, matching `ResultsPanel.tsx`'s current "No decisions identified." pattern) instead of hiding the section.
  - **Quick Actions:** Copy Meeting Summary (serializes title/executive summary/discussions/decisions into readable text, reusing the clipboard pattern already implemented for Copy JSON — `navigator.clipboard.writeText`, success state, graceful fallback message on rejection), Copy Action Items (serializes the action-item list as readable text, same clipboard pattern), Download JSON (reuse the existing serialized `result` already used for Raw JSON), Download Markdown (new — see `lib/meeting/export.ts` below), Generate Follow-up Email (toggles open an inline `<details>`-style block showing `summary.followUpEmail.subject`/`.body` with its own Copy control — no network request, since the draft is already present in `result.summary.followUpEmail` from Task 1).
- New file `lib/meeting/export.ts`:
  - `downloadTextFile(filename: string, mimeType: string, content: string): void` — builds a `Blob`, a temporary `URL.createObjectURL`, a programmatic `<a download>` click, then revokes the URL synchronously after triggering the click (standard pattern; no library).
  - `toMarkdown(result: MeetingResult): string` — a pure formatter producing a readable Markdown document: title/executive summary, decisions, action items (as a table or list, including status), risks, unresolved questions, key moments, next steps, then the full transcript with resolved speaker names and timestamps. Keep it a straightforward template-literal builder consistent with this codebase's existing dependency-free formatting style (`lib/format.ts`) — no Markdown-generation library.
  - Both Download actions in the Output Page call `downloadTextFile` with `toMarkdown(result)` or `JSON.stringify(result, null, 2)` respectively.
- In `components/MeetingWorkspace.tsx`:
  - Pass `audioUrl={previewUrl}` and `audioAvailable={!!audio}` to the Output Page (both already computed/held in this component — no new state).
  - Add `onActionItemsChange(next: ActionItem[])` passed down, implemented as `setResult(prev => prev && prev.summary ? { ...prev, summary: { ...prev.summary, actionItems: next } } : prev)`. No separate "edited action items" state — the existing `result`-persistence effect (`writeStoredValue(LAST_RESULT_STORAGE_KEY, ...)`) already fires on any `result` change, so edits persist across reload for free, and a new Process Meeting attempt replacing `result` wholesale cannot leak edited state between attempts.
  - Extend `isStoredMeetingResult()` to also require `obj.summary === null || typeof (obj.summary as Record<string, unknown>)?.executiveSummary === "string"`, so a `v1`-shaped cached result (e.g. `decisions` as `string[]`) is treated the same as today's "corrupted/outdated entry; ignore" path instead of being restored into the new Output Page with the wrong shape. No migration of old cached values — discarding is sufficient per Technical Design's "Stale cached result handling".
- The Output Page owns one `<audio>` element and `ref` fed by `audioUrl` (rendered only/primarily relevant when `audioAvailable`); a jump control computes the nearest transcript segment via `argmin |segment.startMs - atMs|` (or the segment's own `startMs` when jumping from a transcript row itself) and sets `audioRef.current.currentTime = nearestSegment.startMs / 1000` plus scrolls that row into view. When `audioAvailable` is false, the same controls still scroll the transcript (no playback affordance) rather than being hidden — FR-06's "if audio is still available" qualifier governs the audio playback half only, not the transcript-jump half.

**Risks:** None architectural — this task is UI/presentation work over an already-defined contract. The main implementation risk is scope creep toward the wireframe's excluded chrome (sidebar nav, sync integrations, translate, AI-chat, priority field, speaker-breakdown donut, timeline widget) — Requirement Findings finding 1 and Technical Design's Output Page section already settle that these are out; do not reintroduce them for visual polish.

**Completion:** All four Output Page sections render from a `completed` result with every v2 field, including correct empty-state messages per section. Action-item edits and completion persist in `result` state (and therefore in `localStorage`) without a separate state container. Transcript search/filter and speaker filter work over the full segment list. Both downloads produce a file via the browser's native save flow; both copy actions follow the existing success/fallback UX pattern. A restored `localStorage` result from before this change is discarded, not rendered incorrectly. `bunx tsc --noEmit` and `bun run lint` pass.

## Sequence, decisions and limits

Task 1 can start immediately. Task 2's structure can be built against the Task 1 contract before Task 1's prompt is fully tuned, but meaningful end-to-end review needs Task 1 complete. Task 3 closes the plan. No multi-agent execution is implied by this breakdown.

No open product or architectural decision blocks this plan — Requirement Findings and Technical Design resolved every ambiguity this plan depends on. The remaining uncertainty is entirely about Gemini's actual behavior against the extended schema/prompt (field-fill reliability, name-resolution accuracy, timestamp grounding), which only a real run can resolve; this plan does not pretend otherwise. If a real run surfaces prompt/schema behavior that contradicts an assumption here (e.g., the model cannot reliably return one `speakerNames` entry per listed label), that is new evidence for `1-technical-design` to reconsider, not something to silently patch around with ad hoc client-side heuristics.
